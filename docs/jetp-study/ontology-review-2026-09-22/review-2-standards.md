## Findings

**IATI and CRS are one axis, not two.** Since 2018 OECD requires CRS reporting in an XML built on the IATI schema (crs-in-xml); CRS adds Rio markers, channel, type-of-aid, grant equivalent. Map once, to IATI, and treat CRS as an extension layer. What IATI gives that the draft lacks: **TransactionType separates the flow event from the document** — 12/13 Pledge, 2/11 Commitment, 3 Disbursement, 4 Expenditure — and ActivityDateType 1–4 plus `planned-disbursement` pin planned against actual. What it cannot give: an asset, an agreement object, or a plan. Cost of adoption: none; the draft already keys events separately.

**OC4IDS is the closest structural precedent and the sharpest critique.** It splits `status` (lifecycle: identification → preparation → implementation → completion → maintenance → decommissioning → decommissioned → cancelled) from `type` (intervention kind: construction, rehabilitation, replacement, expansion, decommissioning, maintenance). The draft's `implementation_statuses` in `config/jetp_tracking.yaml` fuses both, and fuses two *subjects*: `preparation`/`procurement` are project states, `operational`/`retired` are asset states. OC4IDS also solves plan-vs-reality with `forecasts[]` and `metrics[]` carrying the **same `Metric.id`** and `Observation` rows — the draft's reconciliation problem, already standardised. OC4IDS's own gaps confirm the draft: no programme parent, no proposition.

**GEM splits below the draft's Asset.** Composite key `{LocationID}_{UnitID}` makes plant and unit two identifier axes, with ownership as `E…` entity IDs and percentages. Coal retirement — the Cirebon-1 question the draft names — is a *unit* fact. A single flat Asset kind cannot carry it. GEM's nine statuses (announced, pre-permit development, permitted, construction, shelved, cancelled, operating, mothballed, retired) define `retired` as "permanently decommissioned **or converted to another fuel**", which the draft's `retired` does not.

**FIBO: do not map tranches.** `SEC/Debt/CollateralizedDebtObligations.rdf` returns only securitization tranches (mezzanine, Z, IO/PO); `LOAN/LoansGeneral/Loans.rdf` has no commitment or tranche class. The draft's disbursement tranche has no FIBO home — use OC4IDS `Finance`.

**Source registers back the draft's money states, not an external code list.** ZAF's JET Grants Register uses pledged / committed / allocated; Climate Funds Update (https://climatefundsupdate.org/about-us/notes-and-methodology/) uses Pledges / Deposits / Approved; CPI and the MDB Joint Report (https://www.adb.org/documents/common-principles-climate-mitigation-finance-tracking) are commitment-basis and never track disbursement. No external list contains `need` or `mou`.

## Answers

**(a) Adopt now — three distinctions.** (1) **Split `implementation_statuses` by subject**, OC4IDS-style: project lifecycle vs asset lifecycle, plus an intervention `type`. Cost: one crosswalk column; benefit: "Tri An expansion on an existing asset" becomes expressible. (2) **Split `financial_statuses` into agreement state and flow type.** `disbursed` sitting beside `mou` is a category error: the first is an event on money, the rest are states of a document. Adopt IATI TransactionType for the event. (3) **Adopt the forecasts/metrics same-ID observation pattern** for plan-line vs realised values.

**(b) The author's own construct is Proposition** — no counterpart in IATI, CRS, OC4IDS (whose `identification` presupposes a decision), or GEM (which folds it into a *status*, "Announced"). **Defend it.** Viet Nam's own RMP splits Annex I's 37 projects from Annex I.2's 181 partner proposals (climate.ec.europa.eu RMP PDF) — the source distinguishes them, so erasing it loses data. A status value cannot express *two* propositions for one future project, nor a death without a project ever existing. But do not mint a seventh table: a proposition **is** an unmatched `plan-projects.csv` line; `matched` should be a dated `prov:specializationOf`/`alternateOf` relation, never a row deletion. That answers the draft's second open call.

**(c) Align the asset half of `implementation_statuses` to GEM's Global Integrated Power Tracker status list** via SKOS `exactMatch`/`narrowMatch`, and the project half to OC4IDS `projectStatus`. GEM is the only register with unit-level retirement across all four countries, so the crosswalk buys external cross-checking on the retirement question directly. Leave `financial_statuses` local and map only the *event* to TransactionType — no external list covers `need`, `announced`, `mou`.
